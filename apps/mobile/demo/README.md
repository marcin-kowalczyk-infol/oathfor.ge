# Simulator demo

Local development fixture for [MVP-05-T12](../../../docs/product/oath-visual-polish.md). From `apps/mobile`, using the Node version in the repository `.nvmrc`:

```sh
npm ci
npm run demo -- --ios --localhost
```

The isolated Expo project serves `demo/index.ts` on port **8082**. The production `index.ts`, app entry and dependencies remain unchanged. Open the available iPhone simulator in Expo Go. `npm run demo -- --localhost` starts the same server without opening a simulator. The launcher's extra arguments are passed to Expo. It requests IPv4-first local DNS so Metro's localhost listener matches the IPv4 address advertised to Expo Go. A caller `--port` replaces 8082. Metro ignores agent worktrees under `.claude/worktrees`, so their edits do not refresh the running demo. Expo Go cannot carry native fixes, so check images in the demo development build described in the [development guide](../../../docs/engineering/development.md#demo-development-build-and-react-native-patch).

A small **DEMO** button opens controls away from the player journey. The demo starts with the empty, onboarded Forge, so the real character creation screen appears first. After a character exists the app shows its own main menu, and "Enter the Forge" opens the app's Forge room. The demo no longer draws a room of its own.

The controls sit under five short headers. Each failure label says what it simulates and when it happens.

The three "lost" and "fails" controls work once. A tap arms the failure, tints the button and shows a "✓ Armed" / "✓ Uzbrojone" line right under it with the next step, for example "Now make an Oath in the Forge". The line stays until the DUMMY runtime spends the failure or a scenario resets the data. Reopen the controls to see it gone.

The PL/EN choice is also the app's default language until the profile loads and after sign-out, so a device set to another language does not flash through. Returning data includes three current Oaths and 22 historical records for pagination. Player characters are DUMMY too. The returning player has two characters, Radomir (active, owner of all returning Oaths) and Wiesna, so the menu card and the change-character screen can switch between them or add a third. Radomir uses starter 2 in the thin build and Wiesna starter 3 in the heavy build. The DUMMY character client offers the six owner starters `starter_01` to `starter_06`, accepts the `thin` or `heavy` build, replays a repeated creation request only when name, preset, build and form match, and uses deterministic IDs. The lost reply to the next Oath also applies to character creation when it comes first. "Simulate: saving on this phone fails after the next Oath" ("Symuluj: po następnym złożeniu Przysięgi zapis na telefonie się nie uda") fails only the next clear of the device acceptance record. After it, a committed Oath is confirmed by the server but its device record stays, so the screen shows the made Oath with the "already made" line and Check confirmation as an outline action. That check replays the same identity and clears the record. Adding an Oath while a pause review in Settings is open allows checking stale revision handling. Pull Today down, or leave and return to the app, to fetch the added record. Going back online in the controls counts as a network reconnect and reloads the visible list, because the simulator's own connection does not drop.

All authentication, API responses, service time and persistence are **DUMMY**, isolated in `runtime.ts`. No credentials or live API calls are used. Rule text and policy come directly from the authoritative `apps/api/resources/oath/workout_oath_v1.json`. The demo does not carry a second copy of policy. Interface restart preserves in-memory pending confirmation, the room guide flag and the art style, while scenario reset, Metro reload and process restart lose all data. The demo cannot establish SecureStore/Keychain persistence, Apple authentication, real backend ordering/reconciliation, delivery, proof or rewards. Its local-time resolver is a deterministic walkthrough substitute, not the production authority. Native permission adapters are inert.

The launcher explicitly sets `NODE_ENV=development` and `OATHFORGE_DEMO=1`. Configuration rejects missing flags and production. Metro additionally rejects every `dev=false` bundle request; the entry guards DUMMY initialization with `__DEV__`. The production entry has no reference to this isolated project.

```sh
npm test -- --runInBand demo
# From demo/; must fail with “development-only”:
NODE_ENV=production OATHFORGE_DEMO=1 node ../node_modules/expo/bin/cli export --platform ios
```

Verified during implementation: focused tests, TypeScript, live iOS development bundle from port 8082, rejected production export, and HTTP 500 for a `dev=false` bundle. Native visual/accessibility verification is recorded separately in the task evidence; bundling is not native acceptance.

## Simulator walkthrough (pending native acceptance)

1. On the empty Forge, create a character, enter the Forge from the menu, touch the hearth and create an Oath, choose activity, pick completion date/time, optionally search/change timezone, then view rules. Return to the Forge, touch the hearth again and verify the draft remains.
2. Read the promise, activation, completion, receipt cutoff and both evidence alternatives; scroll through every rule. Only the final explicit action commits. Open the resulting detail and compare the stored times.
3. In demo controls select the returning scenario. Enter the Forge from the menu, open the seals and one Oath detail, compare it to the full list, then inspect History and load the second page.
4. In Settings, open the pause row and review every withdrawal/preserve row. Adding a synthetic Oath from demo controls before confirming exercises the changed-revision review. Resume and check withdrawals remain in History.
5. Arm a lost reply before confirmation; recover it without creating a second Oath. Toggle offline to exercise retry; expire the session to exercise reauthentication. These are DUMMY scenarios, not real transport/provider evidence.
6. Repeat in EN, at a smaller supported simulator size, with system larger text and Reduce Motion. Check VoiceOver reading order, selected values, error announcement and focus where the simulator supports it. Record actual runtime/settings and blockers; do not substitute static font scaling for native acceptance.

## Proof

An active Oath's detail opens the app's proof screen (MVP-07-T09). The picker, the image manipulator and the cache copy are real, so the camera, Photos and the resize run as in the app. The receipt is DUMMY: `runtime.ts` answers like the API, in the order replay by `submissionId`, receipt cutoff, then state, and turns the Oath `proof_pending` with a queued proof. No image is read or kept by the DUMMY server. The unresolved-proof record is DUMMY memory like the acceptance record, so an interface restart keeps it and the app sends it again when it loads.

To check an interrupted upload, either go offline before sending (nothing is recorded, the copy waits) or arm "Simulate: the reply to the next proof gets lost in transit" (the DUMMY server records the proof but the answer is lost). Then go online or restart the interface. The app resends the same `submissionId` and the DUMMY server returns the original receipt. The simulator has no camera, so only the Photos route can be observed there.

For the MVP-07-T10 states, send a proof through Photos. The detail then shows the assessment note and the receipt time. To see the interrupted upload, go offline before sending. The copy and its record stay on the device. Go back online, then choose "Back to the Oath". The still active Oath shows the interrupted upload with Send again and Delete the copy on this device, and its Today row shows it with Send again. An interface restart resends the record on load, so check the interrupted state before restarting. After the lost proof reply the server holds the proof, so "Back to the Oath" shows the receipt without an interrupted line, and the app replays the same `submissionId` once quietly to clear the record. The demo has no clock control, so a stale record refused after the cutoff is covered by jest tests only. "Add an Oath that needs more proof" ("Dodaj Przysięgę, która wymaga uzupełnienia dowodu") seeds one `needs_more_evidence` Oath for the active character, for checking its seal, Today row and detail. It started six hours ago, its deadline passed two hours ago and its receipt cutoff 15 minutes after that. It holds a timely photo receipt from one hour before the deadline. The client contract has no adverse assessment, correction window or reason code until MVP-08, so the server data carries a receipt with assessment `queued` and an empty reason. The detail shows receipt facts only for `proof_pending`, so it does not show this receipt. A new proof on it is refused, because corrections arrive in a later slice. Pull Today down to fetch it. These new native modules need a new demo development build.

### DUMMY wire check (MVP-07-T11)

The control "Developer check: send proof to a local test server (DUMMY)" under Tools switches only the proof send to the real `createProofClient` and its upload request. It posts the real multipart body to `http://127.0.0.1:18099`, set once in `wireCheck.ts`. The bearer is the DUMMY string `WIRE_CHECK_BEARER`, never the demo session token. Plain HTTP passes the request guard only in a development bundle and only on loopback. The demo development build already allows local HTTP through the Expo template's `NSAllowsLocalNetworking`. Authentication, Oaths, characters and the proof record stay DUMMY, and the offline control still stops the send. A capture server that answers 503 keeps the copy. Do not answer 401, because the client then ends the demo session. With 503 the interrupted state and the resend of the same `submissionId` stay visible. The switch is a transport setting, so a scenario change keeps it. A Metro reload clears it. The capture server is a developer script outside the repository.

## Forge room

The room is the app component `src/forge/ForgeRoom.tsx` with `src/forge/StationEffect.tsx`, reached through the main menu. Its copy lives in the main catalogs under `room`, and `demo/locales` keeps only the controls copy. The active character walks to each place and Żaromir stands aside, so the returning player (Radomir, pilot sprites) shows the full [Forge scene](../../../docs/product/forge-scene.md). Palenisko/Hearth, Pieczęcie/Seals, Kronika/Chronicle and the door each play a distinct decorative response. Arrival never creates an Oath or grants rewards. The dialogue panel's named action flies the camera into creation, current Oaths or history. One touch on Żaromir gives a hint and two counters from the demo counts. "Return to the Forge" goes back to the room while the Oath screens stay mounted, so drafts and unresolved acceptance survive. The moonlit door is a visit whose action returns to the menu. The four-step guide starts on the first room entry of each scenario. The DUMMY runtime keeps its "seen" flag in memory per account, in place of the app's device storage. Interface restart keeps it and a scenario reset clears it. The menu's Tutorial tile replays the guide. At large text or on a narrow window the app uses its simple layout, where "Enter the Forge" opens the Today list directly.

Artwork is provisional. Żaromir uses eight walk directions, a breathing loop, a pose facing each place, a turn and talk gestures over a room backdrop. Each place plays a sprite response on arrival, candles flicker and the seal drums are cut out so he can stand behind them in the doorway. See the [Forge motion assets](../../../docs/art/forge-motion-assets.md). Screens hidden behind the visible one are motion-suspended. See the [room handoff](../../../docs/art/forge-stations-prototype.md) and the [places manifest](../../../docs/art/forge-places-assets.md). No new dependency or external account is required.

## Art style

Settings in the demo has an extra row, Oblicze Kuźni / Face of the Forge, with Dawne / Classic and Filmowe / Cinematic. It switches every screen between the current art and the [cinematic style](../../../docs/art/cinematic-assets.md). Where a cinematic file is missing, the current v01 file shows. Today 85 of the 99 files are cinematic: Żaromir, the room and its cuts, the player figures, portraits and pilot sheets, the station close-ups, the Settings tile, the dialogue panel, icons and the Oath art. Nine light sheets stay classic, see the [manifest](../../../docs/art/cinematic-assets.md#missing-cinematic-files).

`runtime.ts` injects the choice as `artStyle`, like the network adapter. `AuthScreen` reads it once on mount and provides the art to all screens, and the row appears only when the adapter exists. The production app has neither the adapter nor the row. The DUMMY state keeps the choice in memory like the guide flag: interface restart keeps it, a new scenario starts with the cinematic art, onboarding included (owner decision, 2026-09-30). Its copy lives in the main catalogs under `settings.artStyle`.
